# TODO — OPENBSD/

Backlog for the OpenBSD production deploy/ops layer, generated by a
manual audit (2026-07-15) — there is no automated scanner for this
directory the way MASTER has `rake selftest`/`rake constitution`. See
`MASTER/TODO.md` and `RAILS/TODO.md` for the equivalent backlogs on those

Read `README.md`, `START_HERE.md`, `RUNBOOK.md`, `DECISIONS.md`,
`RECIPES.md`, `SSH_ACCESS.md`, `PATH_OWNERSHIP.yml` before touching

## Top 3 — verified bugs, fix these first

   by running it directly. Root cause: `vps_safety_gate.rb:6` sets
   `TOOLING = File.join(ROOT, "OPENBSD")`, then lines 17/20/23/34 build
   paths like `File.join(TOOLING, "sh", "validate_doas.ksh")` — but
   `OPENBSD/sh/` doesn't exist; the real files (`validate_doas.ksh`,

   ```
     - missing OPENBSD/validate_doas.ksh
     - missing OPENBSD/vps_console_common.exp
   ```
   Worse: the `Dir.glob(File.join(TOOLING, "sh", "vps_console*.exp"))` at
   line 23 also uses the wrong prefix, so it silently matches **zero
   files** — the actual safety property this gate exists to enforce
   ("every `vps_console*.exp` sources `vps_console_common.exp` and calls
   `require_console_risk_ack`") is not being checked at all right now. It
   happens to hold today by inspection, but nothing would catch a
   regression. **Fix: drop the `"sh"` path segment at lines 6, 17, 20, 23,
   34.**

2. **Two undocumented, hidden "shadow" deploy scripts bypass every safety
   rail the real deploy path has.** `.deploy_now.sh` and
   `.deploy_manual.sh` (top-level dotfiles, `ls -la` only) aren't
   referenced anywhere in RUNBOOK/RECIPES/START_HERE/SSH_ACCESS.
   - `.deploy_now.sh` hardcodes a **stale VPS IP** (`185.162.251.62` vs.
     the canonical `46.23.89.226` used everywhere else), a Windows-style
     key path (`G:/priv/passwd/id_rsa`), does `rm -rf pub4 && git clone`
     on the VPS, and runs `doas sh openbsd/openbsd.sh` — a lowercase path
     from before the `DEPLOY → OPERATOR → OPENBSD` rename
     (`DECISIONS.md:9`) that no longer exists. Dead, should be deleted.
   - `.deploy_manual.sh` has the correct IP but: does
     `git add -A && git commit && git push origin main` unconditionally
     (violates this repo's own scoped-commit convention), runs
     `ssh -o StrictHostKeyChecking=no` (disables host-key verification —
     a real MITM regression vs. `SSH_ACCESS.md`'s `VerifyHostKeyDNS=yes`
     guidance), and runs `OPERATOR.sh` over SSH **without tmux**, directly
     contradicting `RUNBOOK.md`'s "always use tmux" rule. This is a
     second, undocumented deploy path with weaker safety guarantees than
     the primary one.

   These are destructive/security-relevant to touch — flagging them here
   rather than deleting them outright. Recommend deleting `.deploy_now.sh`
   entirely and either deleting `.deploy_manual.sh` or bringing it up to
   the same safety bar as the documented path (tmux, host-key checking,
   scoped commits) before it's used again.

3. **`OPENBSD/tools/apartments.rb` is broken and unrelated to ops.**
   `require_relative '../lib/scraper'` resolves to `OPENBSD/lib/scraper.rb`,
   which doesn't exist anywhere in the repo — confirmed via `find` and by
   actually requiring the file (`LoadError`). It also requires `mail`,

   scraper, not deploy tooling. `tools/vulcheck.rb` (mobile

## 2. Cross-reference: the RAILS `@`/`_` script rename is only half-done

and `BPLAN/` deploy that code to the VPS, a real bug surfaced while
checking this is worth recording here:

`RAILS/` now has **both** `@*.sh` and `_*.sh` files. `@deploy.sh` was

Worse: `RAILS/_deploy.sh` (the new canonical orchestrator) sources the
`_*.sh` files, while `BPLAN/rails/bplan.sh:22-27` still sources the
**old** `@core.sh`/`@sync.sh`/`@runtime_gate.sh`/`@service.sh` directly —
two parallel, silently-diverging copies of the same logic with two
different callers pointing at two different copies. Also, the new
`_scaffold.sh`, `_runtime_gate.sh`, `_sync.sh`, `_service.sh` files still
have self-referential header comments naming the old `@`-prefixed

this rename is effectively an OPENBSD-deploy correctness issue — see
restructuring section below. `RAILS/TODO.md` now cross-references this
entry rather than duplicating it.

## 3. Error handling / safety

`set -e`/`set -euo pipefail` coverage is good across most top-level
scripts. Missing in `emergency_cpu.sh` (intentional — recovery script uses
`pkill ... || true` and must keep going past "no such process"),
`stale_ci_cleanup.ksh`/`validate_doas.ksh` (sourced function libraries,
`set -e` would be wrong there), and:

- **`manual_master_deploy.ksh` — a genuine gap.** Line 30-31,
  `bundle34 exec rails assets:precompile` has no failure check, and the
  whole script has no `set -e`. If precompile fails, execution falls
  through to `master_web_assets_gate.rb` (line 33, might catch it) and
  then **unconditionally** restarts `master` (line 37) and prints
  `DONE $(date -u)` (line 59) regardless of whether earlier steps failed
  — it can report success after silently deploying stale/missing assets.

Ruby gate scripts mostly have sparse `rescue` usage by design
(`integrity_gate.rb` etc. wrap subprocesses in `Open3.capture2e` and check
`status.success?` rather than raising, so real errors surface as gate
failures, not backtraces) — `health_check.rb` (1 begin/3 rescue in 219
lines) is the only one with real exception handling. Worth a note that an
unhandled exception mid-gate (e.g. `Dir.glob` on a permission-denied path)
would still produce a raw backtrace instead of a clean failure message in
the other 7 gate scripts.

**Hardcoded IPs**: `46.23.89.226` (VPS) and `194.63.248.53` (hypervisor)
are hardcoded in many places (`OPERATOR.sh:296-298`, `deploy_all.sh:18`,
`vps_deploy_master.sh:4`, `backup_priv.sh:3`, `.deploy_manual.sh:4`,
`scripts/deploy-diff.sh:12`) — mostly intentional/documented per
`DECISIONS.md` as canonical constants, but means an IP change needs a
multi-file grep-and-replace instead of one config edit. The one genuinely
suspicious hardcoded IP is `.deploy_now.sh:4`'s stale `185.162.251.62`
(Top 3 #2). No hardcoded passwords/API keys/tokens found anywhere;
`sync.rb:32-37` is actually a secret-*redaction* tool (scrubs
`_API_KEY=`/`_TOKEN=`/`_PASSWORD=`/`_SECRET=` before syncing config back
to git) — good practice, not a finding.

  `etc/daily.local`). None are mentioned in RUNBOOK/RECIPES/SSH_ACCESS/

  no doc pointer to "this box already has a watchdog for that, here's

- The generic-utility scripts (item 1) have essentially no header comment
  explaining purpose or when to run.
- **The live crontab has no tracked mirror** anywhere under `etc/`/`var/`,
  unlike `etc/rc.d`/`var/nsd`/`etc/daily.local` — it's installed via a

  isn't under `/etc`).

## 10. Missing architectural pieces

- **Monitoring is better than a first glance suggests** — `relayd-watchdog`
  (5-min), `config-drift-check` (15-min), weekly cert renewal
  (`OPERATOR.sh:536`), weekly log rotation (`etc/newsyslog.conf`), daily
  NSD/backup/DNSSEC pass (`etc/daily.local`). **The real gap: everything
  terminates in local syslog/log files — there is no external/off-box
  alerting** (no email, Slack webhook, PagerDuty, external uptime ping).
  If vm23 goes down, wedges, or loses network, nothing outside the box
  notices; a human has to notice the site is down. Consistent with
  `DECISIONS.md`'s acknowledged 1-vCPU/1GB constraint (no staging env),
  but outage detection is still a real, undocumented gap worth at minimum
  one external uptime check (e.g. a free-tier uptime-robot-style ping
  against `/up` on each app) even without a full alerting pipeline.
- **Disaster recovery is weaker than `RUNBOOK.md` already admits**, and
  digging further than that doc does: **`restore_backups.sh` does not
  restore Litestream/SQLite backups at all**, despite its name and its
  apparent pairing with `backup.sh` in RUNBOOK's Recovery section. Its
  actual content is a local repo-archaeology tool — rsyncs `MASTER` →
  `pub`, extracts `.tgz`/`.zip` archives found anywhere in the repo, and
  parses old pub3-era installer heredocs — and references a **stale
  path**, `$ROOT_DIR/MASTER/RAILS` (line 51), which no longer exists
  (`RAILS/` moved to top-level per `DECISIONS.md`). There is no real,
  tested "restore from Litestream backup" procedure — the script an
  operator would reach for by name doesn't do that job, and would
  additionally fail/no-op on its stale path. `RUNBOOK.md:136-141` already
  flags Litestream as same-disk-only (not real DR) and recommends an
  off-host replica — that recommendation stands, but even the on-disk
  restore path is unverified.
- TLS renewal and log rotation are both real and automated — not gaps
  (confirmed `usr/local/bin/renew-certs.sh` + `etc/newsyslog.conf`).

## Aggressive restructuring (renaming, flattening, decoupling, merging)

- **Fix `vps_safety_gate.rb`'s path bug first** (Top 3 #1) — it's a
  one-line-per-reference fix (drop `"sh"` from lines 6/17/20/23/34) that
  turns a currently-inert safety check back into a real one. Highest
  value-to-effort ratio in this whole document.
- **Finish the RAILS `@`/`_` script rename** (item 2) — delete
  `RAILS/@core.sh`, `@database.sh`, `@runtime_gate.sh`, `@scaffold.sh`,
  `@service.sh`, `@sync.sh` (keep them only as thin shims if something
  external still needs the old name, matching `@deploy.sh`'s pattern),
  update `BPLAN/rails/bplan.sh:22-27` to source the `_`-prefixed
  canonical versions, and fix the copy-pasted header comments in
  `_scaffold.sh`/`_runtime_gate.sh`/`_sync.sh`/`_service.sh` that still
  name the old file. This is the single highest-value DRY fix found
  across all three audits — two silently-diverging copies of the same
  deploy logic, with two different callers, is exactly the kind of bug
  that turns into a 2am production incident.
- **Flatten `bin/` + `scripts/` + `tools/` from three "where do
  executables go" locations to two.** Move `scripts/deploy-diff.sh` into
  `bin/` (it's an operator entrypoint, same spirit as `bin/vps-state`) and
  delete the now-empty `scripts/` directory. Delete the broken/unrelated
  `tools/apartments.rb`, `tools/vulcheck.rb`, `tools/convert_python.rb`
  (Top 3 #3) — if any are still wanted, they belong in a personal-scripts
  location outside a production ops tree, not here. Keep `tools/tree.rb`
  (it's the one file with a real deploy-tooling purpose), and consider
  whether `tools/` should be renamed/removed once it's down to one file —
  same "single-file directory" smell as `scripts/`.
- **Relocate the personal-utility scripts out of the ops tree entirely.**
  `clean.sh`, `lint.sh`, `perms.sh`, `replace.sh`, `open_in_vim.zsh`,
  `key_bindings.zsh`, `watch_tests.sh` have no OpenBSD/VPS content and
  read like laptop dotfiles that ended up in a production directory.
  Either move them to a personal dotfiles location, or namespace them
  under a clearly-separate `OPENBSD/dev/` so "runs on vm23" and "runs on
  my laptop for editing convenience" aren't mixed in one flat directory.
  Fix `key_bindings.zsh`'s broken shebang (stray
  `# frozen_string_literal: true` on line 1) regardless of where it ends
  up.
- **Delete the two shadow deploy scripts** (Top 3 #2) —
  `.deploy_now.sh` outright (stale IP, dead target path, dead key
  reference), and either delete `.deploy_manual.sh` or bring it up to the
  documented path's safety bar (tmux, host-key checking, scoped commits)
  before anyone runs it again. Two undocumented deploy paths with weaker
  guarantees than the primary one is a decoupling failure in the opposite
  direction — parallel paths that should have been unified into
  `deploy_all.sh`/`OPERATOR.sh` instead of forked.
- **Collapse the 9 near-identical `vps_console_*.exp` scripts into one
  parameterized script** (`vps_console.exp <mode>`, modes = fix_key /
  install / poll_install / probe / short / start_install / status /
  sync_and_install / drop_install) sharing the common-guard/risk-ack
  boilerplate once instead of 9 times. This directly closes the gap
  behind Top 3 #1's safety property — one script means the boilerplate
  literally cannot drift between copies, instead of relying on a
  currently-broken glob to catch drift after the fact.
- **`restore_backups.sh` needs to be split into what its name promises
  and what it actually does.** Rename the current content
  (repo-archaeology/pub3-heredoc extraction) to something like
  `extract_legacy_installers.sh`, and write a real
  `restore_backups.sh` that actually restores from the Litestream/SQLite
  backup path `backup.sh` produces — closing the disaster-recovery gap

  down the wrong path during an actual incident.
- **Merge `data/debt.yml` and this `TODO.md` into one open-items source
  of truth.** Two trackers for "open work on the ops layer" (one YAML,
  one markdown) invites drift the moment either is updated without the
  other. Either fold this TODO's items into `debt.yml`'s schema (tagged
  `agent-ignore`/`operator-priority` like MASTER's `DEBT.md` legend
  already does) or have `debt.yml` point at this file's headings instead
  of duplicating status — pick one direction rather than maintaining both.
- **Audit the deploy scripts for a shared "ssh to vm23 and run X"
  helper.** Several scripts under item 1 (deploy orchestration group)
  likely hand-roll similar SSH/rsync connection setup — worth factoring
  the common connection/retry/tmux-wrapping logic into one `lib/`
  helper (alongside the existing `gate_environment.rb`/`gate_result.rb`/
  `deploy_inventory.rb`) rather than repeating it per script, the same
  DRY move already done for the gate scripts.
