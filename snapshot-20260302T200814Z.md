# MASTER2 Snapshot Analysis (2026-03-02T20:08:14Z)

## High-level read

MASTER2 appears to be a **constitutional AI coding agent runtime** written in Ruby, with explicit policy controls and self-improvement loops.

At a system level, it combines:

- agent orchestration (multiple reasoning patterns)
- policy/governance (axioms + capability levels)
- tool use (file I/O, shell, analysis)
- iterative repair (test → patch → retest)
- adversarial review (council/challenge phases)

## What is most solid

1. **Capability separation exists** (`propose` vs `write` vs `execute` vs `deploy`).
2. **Governance is data-driven** (YAML sources for axioms/models/personas/prompts).
3. **Evidence-first direction is present** (`ToolResult` hashes, touched files, exit codes).
4. **Adversarial/peer review intent is strong** (challenge passes + council semantics).
5. **Fail-visible philosophy is explicit** (better than silent rescues common in agent projects).

## Primary risk concentrations

### 1) Classification-driven privilege escalation

If intent/profile classification can raise capability floors automatically, then misclassification becomes a security issue, not a UX issue.

**Risk:** chat-like input misread as ops/refactor can unlock write/exec.

### 2) Multiple execution pathways

If code can run both via explicit tools and via implicit stage parsing, auditability degrades and policy bypass risk increases.

**Risk:** side effects happen outside the canonical tool/evidence pipeline.

### 3) Regex-based tool parsing

Regex command grammars are brittle for multiline/quoting edge cases.

**Risk:** parser ambiguity and argument confusion in high-risk operations.

### 4) Test-and-fix loop overfitting

Single-file overwrite patterns plus narrowed test selection can produce local green / global regressions.

**Risk:** symptom patches and architecture erosion over time.

### 5) Sanitization without trust downgrades

Redacting injection strings but continuing with near-verbatim payloads can still pass adversarial intent downstream.

**Risk:** “clean-looking” but still directive compromised context.

## Most likely design faceplants

1. **God modules** in executor/tooling paths that become unrefactorable.
2. **Constitution gaming** (high compliance optics, low correctness).
3. **Claim/evidence drift** where prose says “fixed” without mechanically bound evidence.

## Outside-in wiring improvements (highest leverage)

### A) Make escalation explicit and interactive

- Never auto-raise to write/exec/deploy from classifier output alone.
- Require explicit confirmation for crossing capability boundaries.
- Print capability transitions as first-class events.

### B) One execution door

- Route all side effects through one syscall/tool interface.
- Disable implicit code-block execution pathways.
- Ensure every action produces canonical evidence records.

### C) Structured tool protocol end-to-end

- Replace regex parsing with schema-validated structured calls.
- Keep LLM-facing sugar as adapter only.

### D) Bind claims to evidence objects

- Generate “ran/wrote/fixed” statements from tool result records only.
- Refuse success verbs when no evidence object exists.

### E) Risk-based council triggers

- Trigger deep review on risk events (write/exec/external IO), not only “hesitation.”

### F) Harden `needs_review`

- If confirmation gate is unavailable, block by default.

## Practical priority order

1. **Stop automatic capability elevation.**
2. **Unify execution path + evidence model.**
3. **Finish structured tool protocol migration.**
4. **Broaden post-fix validation suite.**
5. **Apply trust downgrades to sanitized content.**

## Bottom line

MASTER2 is not a toy; it is an ambitious agent operating environment with real policy architecture.

The biggest remaining gap is less about missing safeguards and more about **wiring consistency**:

- one authority for permissions,
- one authority for execution,
- one authority for evidence.

Tighten those three and operator trust rises dramatically.
